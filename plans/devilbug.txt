Confirmed — this is the actual root cause of the WallLight (and it's a well-documented pattern bug in this exact codebase that just wasn't fully applied everywhere).

Root cause
WallLight.gd (tile_id 5) is registered in GhostModelBuilder.PROCEDURAL_PREVIEW_SOURCES — the system that builds a real, live instance of an object to show as a spinning preview thumbnail in the Build Mode "Construct" menu. That system explicitly documents the exact failure mode we're chasing:

"a previous version instantiated these same scripts with no guard and registered 3 real running generators into the live PowerManager the instant Build Mode opened"

The fix for that was an _is_preview_only flag, set by the preview builder before add_child(), which every affected script is supposed to check and skip its real registration logic if true. Stove.gd implements this correctly:

gdscript
var _is_preview_only: bool = false
func _ready() -> void:
    ...
    if _is_preview_only:
        return
    call_deferred("_register_deferred")
WallLight.gd never got this guard. It has no _is_preview_only variable at all, so GhostModelBuilder.build_real_instance()'s inst.set("_is_preview_only", true) silently does nothing (Godot no-ops a set() on a nonexistent property). WallLight's _ready() proceeds unconditionally into call_deferred("_register_wire_deferred") → registers a real, live wall light with the actual PowerManager — every time the Construct menu builds its preview thumbnails, using whatever incidental local position the preview pivot ends up at.

Your console log confirms it exactly:

[LIGHT] _register_with_power_manager — id=1023292741410 pos=(-1.034901, -1.332731, 1.034912) ...
That fires right after the generator-tier previews build ([GEN] _ready fired — tier=0/1/2) — same preview pass, same mechanism. And the position (~-1, -1.3, 1) is near world origin with negative Y — underground, north-east-ish of the bunker — matching exactly what you've been seeing.
