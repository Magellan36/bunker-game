Fix Plan: "Space Occupied" Regression on Water Sink / Dispenser / Battery Placement
Verified against a fresh git clone of Magellan36/bunker-game @ main (commit 67a127c, "Fix: Floor-standing objects... now place at ground level" — the previous plan's own commit). Everything below is confirmed against live code, not assumed.

Root cause (confirmed, not speculative)
The previous plan correctly fixed the visual floating bug by adding WATER_SINK_PLACEMENT_Y/WATER_DISPENSER_PLACEMENT_Y/BATTERY_PLACEMENT_Y (all 0.0) and wiring them into GhostPreview.gd's _update_ghost(). That part is live and correct.

But it never touched BuildModeController._is_position_occupied_for_tile() (line 2547). That function already has explicit, hand-written exemptions for TILE_LIGHT, TILE_SHELVING, TILE_BED, TILE_TRAY_SINGLE/DOUBLE, and TILE_GEN_S/M/L — each with its own comment explaining that the generic physics-shape occupancy query (_is_position_occupied(), line 2669, a real PhysicsDirectSpaceState3D overlap query) false-positives against the floor collider itself for anything sitting at floor height. Direct quote from the live Generator branch:

if tile_id == TILE_GEN_S or tile_id == TILE_GEN_M or tile_id == TILE_GEN_L:
	# Generators sit on the floor (Y=0). The physics shape query hits the
	# floor collider and the generator's own StaticBody3D, causing false
	# "space occupied" positives. Use registry-only overlap check instead.
TILE_WATER_SINK, TILE_WATER_DISPENSER, and TILE_BATTERY_S/M/L were never added to this exemption list. Before the previous fix, they placed at Y=2.0 (up near wall height, nowhere near the floor collider), so this false-positive never triggered — the "space occupied" bug was invisible until their Y was correctly moved down to 0.0, at which point they started hitting the exact same floor-collider false-positive that Generators/Beds/Shelving/Trays already needed a fix for. This is a secondary regression the previous plan introduced by fixing one symptom without checking the function that gates placement validity.

Confirmed the exact mechanism holds for all three: WaterTestSink.gd, WaterDispenser.gd, and BatteryBank.gd are all extends StaticBody3D with their own collider (BOX_SIZE = (0.35,0.30,0.35), (0.45,0.55,0.35), and per-tier (0.40,0.70,0.22)/(0.50,0.90,0.26)/(0.60,1.10,0.28) respectively) — placing that collider right at floor height is exactly the "hits the floor collider and the object's own StaticBody3D" scenario the existing comments describe.

Bonus finding while verifying: MoveDuplicateTool.gd (the Move-tool equivalent of GhostPreview.gd) was never updated by the previous plan at all — its own Y-dispatch still sends TILE_WATER_SINK/TILE_WATER_DISPENSER/TILE_BATTERY_S/M/L (and TILE_HEAVY) to the stale PLACEMENT_Y = 2.0. Relocating any of these objects with the Move tool today would make them jump back up to floating height. Not yet reported by you, but it's the same bug family and should be fixed in the same pass.

Second bonus finding: TILE_HEAVY (debug-only HeavyConsumerTest) is confirmed still floating — grouped with TILE_WIRE/TILE_TERMINAL under PLACEMENT_Y=2.0 in GhostPreview.gd line 426-428 (wire/terminal are legitimately wall/panel height; heavy is a floor box and shouldn't be there). The previous plan flagged this as "worth a quick check" but never resolved it.

Part 2 — The systemic fix you asked for: one shared "floor placement" system
You're right that this is the 3rd+ time a floor-height bug has been hand-fixed one object at a time (GEN_PLACEMENT_Y, SHELF_PLACEMENT_Y, now WATER_SINK_PLACEMENT_Y/WATER_DISPENSER_PLACEMENT_Y/BATTERY_PLACEMENT_Y, and 5 separate hand-copied occupancy-check branches). This project already has an established pattern for exactly this kind of thing — BuildModeController.gd has several small _owner-back-reference extracted slices (BuildMaterials.gd, BuildUndoStack.gd, GhostPreview.gd, MoveDuplicateTool.gd, WallSnapHelpers.gd) — this proposal adds one more, following that exact convention, rather than inventing a new architecture style.

This part is a separate, later commit — do not bundle it with Part 1. Part 1 fixes the fire; Part 2 is the "stop this from recurring" follow-up, and touches several already-working code paths that don't need to be at risk while Part 1 is being verified.
